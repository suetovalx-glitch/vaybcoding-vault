# План переезда на VPS на день 2026-09-25

> **Контекст:** VPS куплен (Финляндия), локация и факт покупки известны, но **IP, логин, порт, способ входа, характеристики — пока не присланы**. План построен так, чтобы начать с того, что не зависит от VPS, и плавно перейти к нему, как только придёт доступ.

## Главная цель дня

**Достичь Фазы 4.6 (Smoke-test 1)** из плана `2026-09-24-план-переезда-агента-на-vps.md` — это «агент видит vault и отвечает» на VPS.

## Предусловия (что нужно для старта)

- [ ] **IP VPS** (публичный IPv4).
- [ ] **Порт SSH** — стандартный 22 или нестандартный (например, 22022 из плана).
- [ ] **Логин** — `root` или сразу пользователь (если провайдер создал не-`root`).
- [ ] **Способ входа** — пароль / SSH-ключ (что прислал провайдер).
- [ ] **Характеристики** — RAM, CPU, диск, ОС (Ubuntu 24.04? Debian 12?).
- [ ] **Локация пинга** — Варшава или Финляндия (план рекомендовал Варшаву для OpenAI/Anthropic, но если LLM-провайдер не критичен — Финляндия ок).

> Если что-то из этого придёт **в течение дня** — двигаемся по основному плану. Если **не придёт до вечера** — переключаемся на резервные задачи.

## Утро (до обеда): подготовка

### Блок A. Сбор данных о VPS (15 минут)

1. Собрать всё, что уже известно о VPS в одно место — `wiki/sources/2026-09-25-vps-specs.md`:
   - Провайдер, тариф, цена.
   - Локация, пинг до Москвы / Варшавы / Амстердама.
   - ОС, версия.
   - RAM, vCPU, диск.
   - Лимиты трафика, политика бэкапов, политика восстановления.
2. Если провайдер **не** Amvera/AdminVPS/Timeweb/Selectel — добавить обзор по аналогии с `2026-09-24-adminvps-обзор.md`.

### Блок B. Подготовка ноутбука (20 минут)

1. Найти все пути конфигов pi-coding-agent на ноутбуке:

   ```bash
   ls -la ~/.config/pi/ 2>/dev/null
   ls -la ~/.pi/ 2>/dev/null
   ls -la ~/.pi-coding-agent/ 2>/dev/null
   env | grep -i -E 'PI_|ANTHROPIC|OPENAI|OPENROUTER'
   ```

2. Составить **список того, что переносим на VPS**, по примеру Фазы 3.4 плана:

   ```
   ~/.config/pi/config.json
   ~/.config/pi/agents/
   ~/.config/pi/mcp/
   ~/.config/pi/skills/
   ~/.config/pi/sessions/   # опционально
   ```

3. Сгенерировать **отдельный SSH-ключ для VPS** (если ещё нет):

   ```bash
   ssh-keygen -t ed25519 -C "vps-agent-2026-09-25" -f ~/.ssh/vps-agent
   ```

   Публичный ключ (`~/.ssh/vps-agent.pub`) будем добавлять на VPS.

4. Сгенерировать SSH-ключ для GitHub **отдельным шагом** (это делается уже на VPS, Фаза 2.2).

### Блок C. Аудит vault (15 минут)

1. Проверить, что vault готов к переезду:

   ```bash
   cd "C:/Users/AlexSota/Documents/Bases/Вайбкодинг"
   git status          # чисто?
   git log --oneline -5   # история на месте?
   git remote -v       # куда пушим?
   ```

2. Если vault ещё **не в Git** — инициализировать по Фазе 2 плана переезда vault:
   - Создать приватный репо на GitHub (например, `vaybcoding-vault`).
   - `git init`, первый коммит, `git remote add origin`, `git push -u origin main`.
   - **Проверить `.gitignore`** — нет ли там `wiki/secret.md`, `raw/credentials/`, и т. п.

3. Если vault уже в Git — проверить, что в нём **нет секретов** (Фаза 7.6 плана):

   ```bash
   git log --all --full-history -- "*.env" "*.key" "*.pem" "secrets.env"
   # Должно быть пусто или только тестовые
   ```

4. Записать в `Сессии/2026-09-25/аудит-vault.md` — что нашли, что починили.

## День (после обеда): подключение к VPS — как только придёт доступ

> Этот блок **зависит от того, что прислал пользователь**. Если доступ уже есть — делаем сразу после Блока C. Если нет — двигаемся к «Резервным задачам» и возвращаемся сюда вечером.

### Блок D. Первое подключение (10 минут)

 1. Подключиться через MoxaTerm по инструкции `2026-09-24-moxaterm-vps-first-steps.md`.

 2. **Smoke-test 0:** это Linux, есть сеть, есть sudo:

    ```bash
    uname -a
    cat /etc/os-release
    ping -c 3 github.com
    sudo -n true && echo "sudo OK" || echo "need password"
    ```

### Блок E. Фаза 2 плана — подготовка среды (30 минут)

 1. Создать пользователя `agent` (план Фаза 2.1).

 2. Добавить свой SSH-ключ (`~/.ssh/vps-agent.pub` с ноутбука) в `/home/agent/.ssh/authorized_keys`.

 3. **Проверить вход по ключу** из ноутбука:

    ```bash
    ssh -i ~/.ssh/vps-agent -p <PORT> agent@<IP>
    ```

 4. Закрыть root-доступ по паролю (Фаза 2.8).

 5. Установить runtime: Node 24, Python 3.11+, git, ripgrep, fd, jq, tmux, ufw, fail2ban (Фаза 2.6).

 6. Сменить SSH-порт на нестандартный, если провайдер дал 22 (Фаза 7.5).

### Блок F. Фаза 3 — экспорт конфигов (10 минут, уже на VPS)

 1. С ноутбука скопировать публичные конфиги (Фаза 3.5–3.6):

    ```bash
    scp -P <PORT> /tmp/pi-config-public.tar.gz agent@<IP>:/tmp/
    ```

 2. Скопировать `secrets.env` **отдельно** (Фаза 3.7).

 3. Удалить архивы на ноутбуке (Фаза 3.8).

### Блок G. Фаза 4 — установка агента (15 минут)

 1. Клонировать vault на VPS:

    ```bash
    sudo -u agent git clone git@github.com:<user>/vaybcoding-vault.git /opt/agent/work/Вайбкодинг
    ```

    Если репозиторий ещё не публичный — сначала публикуем с ноутбука.

 2. Установить pi-coding-agent (Фаза 4.1 или 4.2 — выбрать по ситуации).

 3. Восстановить конфиги (Фаза 4.3).

 4. **Smoke-test 1 (Фаза 4.6)** — критическая точка дня:

    ```bash
    sudo -u agent bash -c 'cd /opt/agent/work/Вайбкодинг && /opt/agent/node_modules/.bin/pi'
    ```

    Попросить агента: `> Список файлов в raw/`. Если ответ адекватный — **план дня выполнен**.

## Критерии «день провалился» (нормально, не паника)

- VPS-доступ не пришёл → перешли на резервные задачи, это **ок**.
- pi-coding-agent не установился на VPS → откат, перечитываем логи `journalctl` или `/var/log/agent/`, пробуем снова на следующий день.
- Vault оказался с «грязной» историей (секреты в коммитах) → **отдельная задача**, чистим через `git filter-repo`, не блокируем основной план.
