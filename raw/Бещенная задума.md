# Алиса

Сценарий работы Pi с субагентами `server-operator` и `sftp-operator` — это про оркестрацию задач: один агент смотрит за сервером, второй — за передачей файлов. Ниже — готовый сценарий с логикой, шагами и примерами команд, который можно адаптировать под твой стек (VPS, Proxmox, Pi-машина и т. п.).

---

## Общая логика взаимодействия

- **Pi (главный агент)** — принимает задачу, декомпозирует её, распределяет подзадачи между субагентами, собирает результаты, формирует отчёт.
- **`server-operator`** — отвечает за мониторинг и операции на сервере: проверка статуса сервисов, CPU/RAM/диска, перезапуск служб, обновление пакетов.
- **`sftp-operator`** — отвечает за работу с файлами: загрузка/выгрузка, проверка контрольных сумм, валидация прав, очистка временных файлов.

---

## Сценарий 1: «Ежедневный бэкап сайта с проверкой здоровья сервера»

**Цель:** раз в сутки сделать бэкап сайта на SFTP-хранилище, но только если сервер в норме.

### Шаг 1. Запуск от Pi

Pi получает задачу «ежедневный бэкап» и первым делом запрашивает у `server-operator` статус сервера.

text

```text
task: backup-daily
target-server: vps-01
backup-path: /var/www/site
sftp-host: sftp.example.com
sftp-path: /backups
```

### Шаг 2. Проверка здоровья через `server-operator`

`server-operator` выполняет:

- Проверку загрузки CPU/RAM (например, через `top`/`vmstat` или `glances` API).
- Проверку свободного места на диске (`df -h`).
- Статус ключевых сервисов (nginx/apache, MySQL/MariaDB, PHP-FPM).

**Критерии «сервер в норме»:**

- CPU load < 1.5 (для 1–2 vCPU).
- RAM free > 20%.
- Диск свободен > 15%.
- Все сервисы в статусе `active`.

Если критерии не выполнены — `server-operator` возвращает статус `unhealthy`, и Pi **не запускает** бэкап, а пишет алерт.

### Шаг 3. Подготовка архива на сервере

Если сервер в норме, `server-operator`:

- Создаёт архив сайта: `tar -czf /tmp/site-backup.tar.gz /var/www/site`.
- Считает контрольную сумму: `sha256sum /tmp/site-backup.tar.gz > /tmp/site-backup.sha256`.

### Шаг 4. Передача через `sftp-operator`

`sftp-operator`:

- Подключается к SFTP (ключи, без паролей).
- Загружает `/tmp/site-backup.tar.gz` и `/tmp/site-backup.sha256` в `/backups`.
- Проверяет, что размер файла совпадает.
- При успехе — удаляет временные файлы на сервере.

### Шаг 5. Отчёт от Pi

Pi собирает:

- Статус `server-operator`.
- Статус `sftp-operator`.
- Время начала/окончания.
- Размер архива и SHA256.

И формирует краткий отчёт (JSON/Markdown) — его можно слать в Telegram, почту или сохранять в лог.

## Сценарий 2: «Развёртывание обновления с откатом при ошибке»

**Цель:** обновить файлы сайта, но с гарантией отката, если что-то пойдёт не так.

### Шаг 1. Pi: подготовка плана

Pi говорит `server-operator`: «подготовить точку отката» — сделать архив текущей версии сайта и сохранить метаданные (версии пакетов, список файлов).

### Шаг 2. `sftp-operator`: доставка новых файлов

Загружает новую версию сайта из SFTP-источника (или из Git-архива, если SFTP используется как артефакт-хранилище).

### Шаг 3. `server-operator`: проверка и активация

- Проверяет целостность файлов (контрольные суммы).
- Делает минимальную проверку: `curl -I` на главную страницу.
- Если всё ок — активирует новую версию (переключает симлинки, рестартует сервис).

### Шаг 4. Контроль и откат

- Если проверка не прошла — `server-operator` откатывает на точку отката.
- `sftp-operator` может дополнительно загрузить логи ошибок на SFTP для анализа.

### Шаг 5. Финальный отчёт

Pi собирает логи, статус отката/успеха, время, и фиксирует результат.

## Пример структуры конфигурации (псевдо-формат)

yaml

```yaml
agent: pi
subagents:
  server-operator:
    host: vps-01
    check-health: true
    services: [nginx, mysql]
  sftp-operator:
    host: sftp.example.com
    user: backup-user
    key-path: /home/pi/.ssh/id_ed25519
    remote-path: /backups

tasks:
  - name: daily-backup
    depends-on: server-operator.health-ok
    actions:
      - type: archive
        source: /var/www/site
        output: /tmp/site.tar.gz
      - type: upload
        file: /tmp/site.tar.gz
        checksum: /tmp/site.sha256
      - type: cleanup
        files: [/tmp/site.tar.gz, /tmp/site.sha256]
```

## Практические советы под твои интересы (VPS, Podman, Proxmox)

- **Если используешь Podman:** `server-operator` можно сделать отдельным контейнером, который запускается по требованию и имеет доступ к метрикам хоста (через cgroup/metrics API). Это снижает нагрузку на основную машину.
- **Для Proxmox:** если Pi и субагенты живут на разных нодах, лучше использовать SSH-exec или API Proxmox для проверки статуса VM перед началом операций.
- **Безопасность:** не передавай пароли в открытом виде. Используй SSH-ключи, ограничь права SFTP-пользователя (chroot), валидируй контрольные суммы.
- **Логирование:** пусть каждый субагент пишет структурированные логи (JSON), а Pi собирает их в единый отчёт. Это сильно упрощает отладку.

Отлично, теперь я вижу полный контекст — речь про **Pi Agent** (терминальный кодинг-агент от Earendil), работающий на VPS, с расширением **pi-subagents** и двумя субагентами: `server-operator` (SSH) и `sftp-operator` (SFTP). Вот готовый рабочий сценарий на основе паттернов из vibecode-setup.

## Архитектура

text

```text
Pi (главный агент на VPS)
├── .pi/mcp.json          ← конфиг MCP-серверов (ssh-connect, sftp-connect)
├── .pi/agents/           ← определения субагентов
│   ├── server-operator.md
│   └── sftp-operator.md
├── .env                  ← SSH_HOST/PORT/USER/PASSWORD (gitignored)
├── scripts/
│   ├── ssh.sh            → npx ssh-mcp
│   └── sftp.sh           → npx sftp-ssh-mcp
└── deploy/SERVER-DEPLOY.md  ← пошаговая инструкция деплоя
```

**Правило №1:** Pi **никогда** не вызывает `mcp__ssh-connect__*` или `mcp__sftp-connect__*` напрямую. Всё делегируется через `subagent()`. 

**Правило №2:** `server-operator` и `sftp-operator` **не вызывают друг друга**. Их связывает только оркестратор (Pi или `server-deployer`). 

**Правило №3:** Субагенты только исполняют — не интерпретируют. Решение остаётся за Pi: субагент возвращает `stdout/stderr/exit-code`, Pi решает, что дальше.

## Сценарий 1: Диагностика сервера (только чтение)

Pi получает запрос «проверь состояние сервера» и делегирует одной командой `server-operator`.

text

```text
Пользователь: проверь сервер

Pi:
subagent({
  agent: "server-operator",
  task: "Через ssh_connect_exec выполни: `uptime && free -h && df -h / && docker ps --format '{{.Names}}\t{{.Status}}'`. Верни вывод."
})
```

`server-operator` выполняет команды через `ssh_connect_exec`, возвращает сырой вывод. Pi читает результат и формулирует ответ пользователю: «Сервер в норме, load 0.4, RAM 60%, диск 45%, контейнеры запущены».

---

## Сценарий 2: Деплой приложения (полный цикл)

Это основная связка — оркестратор собирает архив локально, `sftp-operator` заливает, `server-operator` распаковывает и запускает. 

### Шаг 0. Pi: сборка архива локально

bash

```bash
tar -czf /tmp/release.tar.gz -C dist .
sha256sum /tmp/release.tar.gz
```

### Шаг 1. Pi → `sftp-operator`: загрузка на сервер

text

```text
subagent({
  agent: "sftp-operator",
  task: "Загрузи локальный файл /tmp/release.tar.gz на сервер в /home/vibecoder/app/release.tar.gz через sftp_connect_sftp_upload. Верни результат."
})
```

### Шаг 2. Pi → `server-operator`: распаковка и сборка

text

```text
subagent({
  agent: "server-operator",
  task: "Распакуй /home/vibecoder/app/release.tar.gz в /home/vibecoder/app/, выполни npm ci и npm run build, рестартни сервис. Верни результат каждой команды."
})
```

`server-operator` последовательно:

- `tar -xzf /home/vibecoder/app/release.tar.gz -C /home/vibecoder/app/`
- `cd /home/vibecoder/app && npm ci`
- `cd /home/vibecoder/app && npm run build`
- `systemctl restart vibecoder-app`

Каждую команду — отдельно, с возвратом exit code и вывода.

### Шаг 3. Pi → `server-operator`: healthcheck

text

```text
subagent({
  agent: "server-operator",
  task: "Через ssh_connect_exec выполни: `systemctl is-active vibecoder-app && curl -sI http://localhost:3000/api/health | head -1`. Верни вывод."
})
```

### Шаг 4. Pi: отчёт

Pi собирает результаты всех шагов и выдаёт структурированный отчёт:

text

```text
✅ SFTP upload: 12.3 MB, sha256 совпадает
✅ npm ci: 450 packages installed
✅ npm run build: completed in 34s
✅ systemctl restart: active (running)
✅ Healthcheck: HTTP 200
Деплой завершён за 2 мин 17 сек.
```

```markdown
Shell on remote host — runs commands via project-local ssh-connect MCP
```

## Типичные проблемы и решения

|Проблема|Решение|
|---|---|
|`ssh-connect` не подключается|Вызови `mcp({ connect: "ssh-connect" })` один раз за сессию. Проверь `.env` и что `scripts/ssh.sh` запускается вручную|
|`sftp-connect` не подключается|То же самое: `mcp({ connect: "sftp-connect" })`. Проверь `npm ls sftp-ssh-mcp`|
|Файл загрузился, но пустой|SFTP upload принимает один файл, не директорию. Сначала `tar -czf`, потом заливай архив|
|SHA256 не совпадает|Проверь `sha256sum` с обеих сторон. SFTP не считает контрольные суммы. Если отличаются — перезалей|
|Порт 3000 занят|`npm run kill:backend` или найди PID через `netstat -ano \| grep :3000`|

---

## Ключевые принципы

1. **Разделение по назначению:** SFTP — для данных (перемещение файлов), SSH — для действий (распаковка, установка, рестарт, проверка). Смешивание создаёт путаницу в логах и аудите. 
2. **SFTP-archived:** `sftp_connect_exec` существует, но намеренно не используется — весь shell идёт через `ssh-connect`. 
3. **Только локальные MCP:** не откатывайся на глобальный `ssh-mcp` из `~/.pi/agent/mcp.json`, даже если он подключён — используй только проектные. 
4. **Креды в `.env`:** никогда не клади пароли в `.pi/mcp.json` или в код. Обёртки `scripts/ssh.sh` и `scripts/sftp.sh` читают `.env`. 
5. **Контекстная изоляция:** каждый субагент работает в изолированной сессии, получает только свою задачу и возвращает только результат — Pi экономит контекст.

## Сценарий 7: Сбор логов упавшего контейнера

Сценарий: Pi видит (или узнаёт от cron-проверки), что контейнер `app-redis` в статусе `Exited`. Надо понять причину.

### Шаг 1. Pi → `docker-operator`: логи контейнера

text

```text
subagent({
  agent: "docker-operator",
  task: "Через ssh_connect_exec выполни: `docker logs app-redis --tail 100 --timestamps 2>&1`. Верни вывод полностью."
})
```

### Шаг 2. Pi анализирует логи

Pi читает вывод, ищет паттерны:

- `OOM Killed` / `Cannot allocate memory`
- `Connection refused` / `port already in use`
- `Permission denied`
- `panic:` / `fatal:` / `FATAL`

### Шаг 3. Pi → `docker-operator`: доп. информация

Если логи не дали ответа — Pi просит детали:

text

```text
subagent({
  agent: "docker-operator",
  task: "Через ssh_connect_exec выполни: `docker inspect app-redis --format '{{.State.ExitCode}} {{.State.Error}} {{.HostConfig.RestartPolicy.Name}}' && dmesg | grep -i 'killed process' | tail 5`. Верни вывод."
})
```

### Шаг 4. Pi → `sftp-operator`: выгрузка логов в архив (опционально)

text

```text
subagent({
  agent: "docker-operator",
  task: "Через ssh_connect_exec выполни: `docker logs app-redis > /tmp/redis-crash.log 2>&1`."
})

subagent({
  agent: "sftp-operator",
```

## Сценарий 10: Проверка ресурсного голодания (OOM-prone контейнеры)

text

```text
subagent({
  agent: "docker-operator",
  task: "Через ssh_connect_exec выполни:
1. `docker stats --no-stream --format '{{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}\t{{.CPUPerc}}'`
2. `docker ps --format '{{.Names}}' | xargs -I{} docker inspect {} --format '{{.Name}} memory_limit={{.HostConfig.Memory}} swap_limit={{.HostConfig.MemorySwap}}'

})
```

Pi анализирует:

- Если `MemPerc > 80%` → предупреждение о скором OOM.
- Если `dmesg` содержит `Killed process` → значит уже был OOM-kill, надо поднять лимиты.
- Если `Memory=0` → лимит не задан, контейнер может сожрать всю RAM хоста.

## Cron-мониторинг: `scripts/docker-monitor.sh`

Скрипт, который Pi запускает по расписанию (через `crontab` или `systemd-timer`):

bash

```bash
#!/usr/bin/env bash
# Запускается каждые 5 минут через cron
# Проверяет контейнеры и пишет результат в /tmp/docker-monitor.last

source "$(dirname "$0")/../.env"

# Быстрая проверка: есть ли упавшие контейнеры?
RESULT=$(ssh -p "$SSH_PORT" "$SSH_USER@$SSH_HOST" \
  "docker ps -a --filter status=exited --format '{{.Names}}\t{{.Status}}\t{{.ExitCode}}'" 2>&1)

if [ -n "$RESULT" ]; then
  echo "[$(date -u +%FT%TZ)] CRASHED:" >> /tmp/docker-monitor.last
  echo "$RESULT" >> /tmp/docker-monitor.last
  
  # Здесь можно дернуть Pi-агента для анализа:
  # pi exec "docker-monitor alert: $RESULT"
fi
```

`crontab -e`:

## Структура чеклиста

10 шагов, от быстрых к глубоким:

|Шаг|Что проверяет|Команды|
|---|---|---|
|1|Состояние контейнеров|`docker ps -a`|
|2|Healthcheck-статусы|`docker inspect .State.Health`|
|3|CPU, RAM, диск|`docker stats`, `docker inspect` memory limits, `df -h`|
|4|Логи на ошибки|`docker logs --since 10m \| grep -iE 'error\|fatal\|...'`|
|5|OOM-события|`dmesg -T \| grep oom`, `memory.events` (cgroup v2)|
|6|Рестарт-шторм|`RestartCount`, `RestartPolicy`|
|7|Размер логов и ротация|`du -sh /var/lib/docker/containers/*/`, `daemon.json`|
|8|Docker-хранилище|`docker system df -v`, `prune`|
|9|Сетевые порты|`ss -tlnp`|
|10|Решения и отчёт|Сводная таблица действий + шаблон отчёта|

## Ключевые решения, заложенные в чеклист

- **Память**: лимит = 150% от пика, JVM heap (`-Xmx`) = 75% от `--memory` — иначе OOM гарантирован. netdata.cloud +1
- **Ротация логов**: значения в `daemon.json` — строки (`"10m"`, не `10m`), применяется только к новым контейнерам. 
- **OOM-диагностика**: `Memory cgroup out of memory` = лимит контейнера, `Out of memory` + `Killed process` = системный OOM хоста. 
- **Рестарт-шторм**: `restart: always` + падающий сервис = бесконечный цикл, который заливает логи. 
- **Healthcheck**: `FailingStreak >= 3` — реальный сбой, `== 1` — возможно временный. 

## Шаблоны вызовов

В приложении — 4 готовых шаблона `subagent({ agent: "docker-operator", ... })`: routine-проверка (раз в 5 мин), глубокая проверка (раз в час), реакция на падение, рестарт с healthcheck.
