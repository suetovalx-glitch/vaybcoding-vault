## Что обычно включают в такие сценарии

Чаще всего это простые цепочки вида «если → то»:

- **Триггер** (событие): время, датчик движения, голос, кнопка, состояние устройства.
- **Условие** (опционально): только если темно, если дома есть кто-то, если температура ниже X.
- **Действия**: включить свет, запустить чайник, открыть шторы, отправить уведомление, запустить плейлист.

Отлично, давай сделаем сценарии именно под Node‑RED — это как раз удобно для умного дома: там логика собирается из нод, а не пишется сплошным кодом.

## Важное перед примерами

В Node‑RED сценарии строятся цепочкой: **Trigger → Condition/Filter → Action**. Для работы с Алисой/умным домом чаще всего используют:

- `inject` / `time` / `mqtt in` — триггеры;
- `switch` / `function` — условия и логика;
- `mqtt out` — отправка команд устройствам;
- готовые ноды типа `node-red-contrib-home-assistant` — если дом на Home Assistant.

## Сценарий 1: «Вечер дома» (движение + время + свет + музыка)

**Цель:** когда в коридоре срабатывает датчик движения с 18:00 до 23:59 и темно — включить приглушённый свет и запустить плейлист.

**Цепочка нод:**

1. `mqtt in`: топик `home/hallway/motion`, payload: `{"state":"ON"}`.
2. `change`: добавить поле `timestamp` (текущее время).
3. `function`: проверка времени и освещённости (упрощённо — считаем, что свет включается, если движение есть).
    
    javascript
    
    ```javascript
    const now = new Date();
    const hour = now.getHours();
    if (hour >= 18 && hour <= 23) {
        msg.validTime = true;
        return msg;
    }
    return null; // не в диапазоне — дальше не идёт
    ```
    
4. `switch`: если `validTime === true` → ветка действий.
5. `mqtt out`: топик `home/living_room/light/set`, payload: `{"brightness":40}`.
6. `mqtt out`: топик `home/hallway/light/set`, payload: `{"brightness":30}`.
7. `mqtt out`: топик `home/speaker/play`, payload: `{"playlist":"Chill Evening"}`.

**Нюанс:** если у тебя есть отдельный датчик освещённости, добавь ещё одну ветку `mqtt in` по топику света и сравнивай значение. В Node‑RED удобно делать это через `join` (ждать два сообщения: движение + свет) и потом проверять оба условия в `function`.

## Сценарий 2: «Утро по будильнику» (время + плавное включение света + кофе + голосовое сообщение)

**Цель:** в 07:00 начать плавное увеличение яркости, запустить кофеварку, сказать «Доброе утро».

**Цепочка нод:**

1. `inject`: интервал раз в день, время `07:00`, payload: `{ "action": "morning_routine" }`.
2. `function`: подготовить список действий с задержками.
    
    javascript
    
    ```javascript
    // Возвращаем массив сообщений для последовательной отправки
    msg.payloads = [
        { topic: "home/bedroom/light/set", payload: { brightness: 20, transition: 60 } },
        { topic: "home/coffee_machine/set", payload: { action: "start_brewing" } },
        { topic: "home/speaker/say", payload: { text: "Доброе утро! Кофе уже готовится." } }
    ];
    return msg;
    ```
    
3. `split`: разбить массив на отдельные сообщения.
4. Три `mqtt out` ноды (или одна с динамическим топиком, если умеешь настраивать).

**Про «плавный переход»:** сам Node‑RED не делает плавное изменение яркости — это делает устройство или MQTT‑брокер/интеграция (например, Zigbee2MQTT, Home Assistant). Параметр `transition: 60` (в секундах) нужно передавать в том формате, который понимает твой контроллер.

---

## Сценарий 3: «Если дома никого нет — выключить всё» (связка датчиков движения)

**Цель:** если в течение 15 минут ни в одной комнате нет движения — выключить свет и отправить уведомление.

**Как сделать:**

1. `mqtt in` для каждого датчика движения (или один общий топик, если все датчики шлют в один).
2. `trigger`: поставить на 15 минут без новых сообщений. Если за 15 минут не пришло новое движение — срабатывает выход.
3. `function`: проверить, что последнее движение было давно (или вообще не было).
4. `mqtt out`: выключить все нужные светильники.
5. `http request` или ещё один `mqtt out` — отправить сообщение в Telegram/уведомление.

Это один из самых полезных сценариев: он реально экономит электричество и снижает ложные срабатывания.

## Как это реально работает на практике

1. **Ты даёшь промпт агенту на pi.dev**: «Напиши сценарий Node‑RED: если датчик движения сработал после 18:00 — включи свет на 40% яркости и запусти плейлист».
2. **Агент возвращает**: JSON‑импорт для Node‑RED, YAML‑описание, список нод с настройками или JS‑код для ноды `function`.
3. **Ты импортируешь** в свой Node‑RED (через Import → Paste) и при необходимости подкручиваешь топики MQTT под свои устройства.
4. **Node‑RED выполняет** автоматизацию, а pi.dev остаётся только как «фабрика идей и кода».

## Docker Compose для Node‑RED и Mosquitto (чтобы всё было рядом)

yaml

```yaml
version: '3.8'
services:
  mosquitto:
    image: eclipse-mosquitto:latest
    container_name: mosquitto
    restart: unless-stopped
    ports:
      - "1883:1883"
    volumes:
      - ./mosquitto/config:/mosquitto/config
      - ./mosquitto/data:/mosquitto/data

  nodered:
    image: nodered/node-red:latest
    container_name: nodered
    restart: unless-stopped
    depends_on:
      - mosquitto
    ports:
      - "1880:1880"
    environment:
      - TZ=Europe/Moscow
    volumes:
      - ./node-red/data:/data
```

С этим стеком ты сможешь быстро разворачивать Node‑RED и сразу подключать его к MQTT — а ИИ (будь то pi.dev или я) будет выдавать готовые сценарии под эту инфраструктуру.

## Вариант 1: Node‑RED прямо на Windows (самый быстрый для тестов)

Подходит, если хочешь быстро попробовать редактор и собрать пару потоков.

### Шаг 1. Установи Node.js (обязательно)

Node‑RED работает поверх Node.js.

1. Скачай LTS‑версию с nodejs.org (для Windows).
2. Запусти установщик, оставь все галочки по умолчанию.
3. Проверь в PowerShell или CMD:
    
    bash
    
    ```bash
    node -v
    npm -v
    ```
    

### Шаг 2. Установи Node‑RED глобально

В PowerShell (лучше от администратора):

bash

```bash
npm install -g --unsafe-perm node-red
```

Флаг `--unsafe-perm` тут нужен, чтобы npm не блокировал установку некоторых нативных модулей на Windows.

### Шаг 3. Запусти Node‑RED

bash

```bash
node-red
```

Он напишет, где лежит папка с флоу (обычно `C:\Users\<твой_пользователь>\.node-red`) и скажет, что редактор доступен по `http://127.0.0.1:1880`.

### Шаг 4. Открой редактор

В браузере: `http://localhost:1880` — это и есть интерфейс Node‑RED.

> **Важно для умного дома:** если планируешь использовать MQTT, на Windows отдельно поставь Mosquitto (MQTT‑брокер) или используй облачный/VPS‑брокер. Node‑RED сам по себе не является брокером.

---

## Вариант 2: Node‑RED в Docker на Windows (ближе к твоему VPS‑стеку)

Если ты уже работаешь с Docker (и тем более с VPS), лучше сразу в контейнере — так флоу и зависимости будут переноситься между системами.

1. Установи Docker Desktop для Windows.
2. Создай папку, например `C:\docker\nodered`.
3. В ней создай `docker-compose.yml`:

yaml

```yaml
version: '3.8'
services:
  nodered:
    image: nodered/node-red:latest
    container_name: nodered
    restart: unless-stopped
    ports:
      - "1880:1880"
    volumes:
      - ./data:/data
    environment:
      - TZ=Europe/Moscow
```

4. Запусти:
    
    bash
    
    ```bash
    docker compose up -d
    ```
    
5. Открой `http://localhost:1880`. Флоу будут сохраняться в `C:\docker\nodered\data`.

Это почти точная копия того, что ты будешь держать на VPS — удобно переносить флоу между машинами.

- **Ноды интеграции** — в Node‑RED через Palette Manager часто ставят `node-red-contrib-home-assistant`, `node-red-node-mqtt` и т.д.
- **Безопасность** — если Node‑RED будет виден не только локально, обязательно поставь авторизацию (в файле `settings.js` или через переменные окружения в Docker).

# Алиса

Тут есть важный нюанс: **pi.dev (как и любой ИИ‑агент в терминале) не может «напрямую писать» в твой Node‑RED** — у него нет доступа к твоему серверу, контейнеру или редактору. Он не подключается к порту 1880 и не редактирует файлы на VPS без твоих действий.

Но он реально может **выдавать готовый результат**, который ты вставляешь в Node‑RED за пару кликов. И это как раз удобно под твой сценарий: ИИ на отдельной машине (pi.dev) генерирует, а Node‑RED на VPS/Windows исполняет.

---

## Как это выглядит на практике: цепочка «терминал → Node‑RED»

1. **В терминале (с pi.dev или мной)** ты пишешь:  
    _«Сделай флоу для Node‑RED: если датчик движения (топик `home/motion`) сработал после 18:00 — включи свет (`home/light/set`, яркость 40%)»_.
2. **ИИ возвращает JSON‑массив нод** (как в примере ниже).
3. **Ты открываешь Node‑RED в браузере** → жмёшь **Import** → **Paste** → вставляешь JSON → **Import**.
4. **Флоу появляется в редакторе**, ты только проверяешь/подкручиваешь топики под свои устройства.

Всё. Никаких скриптов, которые «сами пишут в Node‑RED». Это и безопаснее, и понятнее.

---

## Пример: тот самый JSON, который ИИ отдаёт в терминал

---

## Почему нельзя по‑другому (и зачем это ограничение — это плюс)

- **Безопасность**: если бы ИИ мог сам править файлы или отправлять HTTP‑запросы к Node‑RED, это был бы риск (ошибка, неправильные команды, удаление флоу).
- **Контроль**: ты видишь, что именно добавляется, можешь проверить JSON перед импортом.
- **Переносимость**: один и тот же JSON работает и на Windows, и в Docker, и на VPS.

Учитывая твой план с VPS‑оркестрацией, такой подход даже лучше: **pi.dev = фабрика шаблонов**, **Node‑RED = исполнитель**.

---

## Практический совет: как сделать это максимально удобно

1. **Держи Node‑RED в Docker** (на VPS или Windows) — тогда флоу хранятся в volume (`./data`), и ты можешь их бэкапить/переносить.
2. **Используй короткие промпты** для ИИ:  
    _«Дай JSON‑флоу для Node‑RED: триггер — MQTT‑топик X, условие — время Y, действие — MQTT‑команда Z. Формат — готовый JSON для Import»_
3. **Для частых сценариев заведи шаблоны**: один раз сохранил JSON в файл `motion-to-light.json` и импортируешь его везде, где нужно.
4. **Если хочется автоматизации импорта** (продвинутый уровень): можно написать простой скрипт на Bash/PowerShell, который берёт JSON из файла и делает HTTP‑запрос к API Node‑RED (у него есть endpoint `/flows`). Но это уже отдельный шаг — и он нужен только если ты делаешь много деплоев.

---

## Важное про твой стек (VPS + Docker + WSL)

Если Node‑RED крутится на VPS в Docker, а pi.dev — на отдельной машине:

- **Не пытайся «заставить» pi.dev править файлы на VPS напрямую.**
- **Лучше:** pi.dev отдаёт JSON в терминал → ты копируешь его в браузер на VPS → Import в Node‑RED.
- Это быстрее и надёжнее, чем настраивать SSH/API‑доступ для ИИ.

## Что можно использовать

- **Расширения (extensions).** Это модули на TypeScript, которые добавляют новые инструменты, команды или элементы интерфейса. Например:
    
    - **pi-subagents** — позволяет делегировать задачи «субагентам»: отдельный агент может делать код-ревью, исследовать кодовую базу, выполнять повторяющиеся задачи. hascode.com +1
    - **pi-lens** — запускает LSP-диагностику, линтеры и форматировщики (Ruff, ESLint и др.) прямо при редактировании файла, сразу показывая ошибки и позволяя их исправить. 
    - **pi-web-access** — добавляет возможности веб-поиска, извлечения данных из PDF, работы с GitHub (клонирование репозиториев). 
    - **pi-mcp-adapter** — позволяет подключать внешние инструменты через Model Context Protocol (MCP), не съедая при этом окно контекста агента. 
    - **pi-defender** — перехватывает потенциально опасные команды (вроде `rm -rf`, `DROP TABLE`) и запрашивает подтверждение перед выполнением. 
- **Скилы (skills).** Это пакеты с инструкциями и инструментами, которые агент подгружает по мере необходимости для решения конкретной задачи. Например, можно найти скил для работы с конкретным API, фреймворком или для автоматизации рутинных операций в определённой области. topai.tools +1
    
- **Интеграция с внешними сервисами и приложениями.** Через расширения или MCP можно связать pi.dev с внешними системами. Например, с помощью **Composio** агент получает доступ к тысячам приложений: Slack, GitHub, Notion, Gmail и другим. 
    
- **Работа с моделями и провайдерами.** pi.dev поддерживает множество провайдеров LLM (OpenAI, Anthropic, Google, Azure, локальные модели через Ollama и llama.cpp). Можно в ходе сессии переключаться между моделями командой `/models`. ai.codelab.vc +2
    
- **Режимы работы для автоматизации.** Помимо интерактивного TUI, есть режимы, удобные для скриптов и встраивания:
    
    - **print/JSON** — удобен для скриптов, когда нужно получить структурированный вывод. ai.codelab.vc +1
    - **RPC** — запускает JSON-протокол поверх stdin/stdout, что позволяет встраивать pi в другие инструменты и IDE. ai.codelab.vc +2
    - **SDK** — даёт возможность встроить pi в собственные приложения. ai.codelab.vc +1
- **Управление контекстом.** В pi.dev есть механизмы для работы с большим контекстом: ветвление сессий (можно откатиться к развилке), автоматическое сжатие истории, динамическая инъекция контекста. # Алиса

**Context7 с pi.dev** — это связка, которая даёт агенту в терминале доступ к актуальной документации по библиотекам и фреймворкам прямо во время написания кода или настройки автоматизации (например, для Node‑RED, Docker, скриптов на VPS).

## В чём суть взаимодействия

Без Context7 агент опирается на знания из обучения — они могут быть устаревшими. С Context7 он в реальном времени подтягивает точную документацию и рабочие примеры кода. Для твоего стека (Node.js, Docker, Node‑RED, автоматизация) это критично: версии библиотек меняются, а примеры из памяти ИИ быстро устаревают.

---

## Как технически устроена интеграция

Для pi.dev есть официальное расширение `@upstash/context7-pi`. Оно работает не как «обычный MCP‑сервер», а как нативный навык внутри pi — то есть не нужно отдельно поднимать MCP‑сервис: инструменты регистрируются прямо в агенте.

Ключевые инструменты, которые появляются после установки:

- `resolve-library-id` — превращает название вроде «Next.js» или «Supabase» в внутренний ID библиотеки в Context7.
- `query-docs` — запрашивает актуальную документацию и примеры по этому ID.
- `/c7-docs` — удобная команда в терминале: `/c7-docs next.js Cache Components` сразу вернёт точные фрагменты документации.

---

## Что это реально даёт в твоих задачах

### Для Node‑RED и MQTT

Ты можешь спросить: «Покажи актуальный пример payload для Zigbee2MQTT для лампочки Ikea» или «Как правильно задать transition в MQTT‑команде для этой модели». Context7 подтянет точные поля и примеры, а не «примерно как у всех».

### Для Docker и Node.js на VPS

«Дай правильный Dockerfile для Node‑RED с привязкой к Mosquitto, с учётом последних версий». Агент, имея доступ к документации, будет использовать актуальные образы и переменные, а не старые шаблоны.

### Для скриптов бэкапа и автоматизации

«Покажи, как использовать rsync с этими флагами по официальной документации» — и получишь точные описания опций, а не приблизительные.

### Для вайбкодинга и быстрого прототипирования

Когда ты собираешь MVP или пробуешь новый стек, Context7 помогает не гуглить каждый шаг: агент сам достаёт нужные примеры и сразу вставляет их в код или в JSON‑флоу для Node‑RED.
