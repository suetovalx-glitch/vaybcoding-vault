## Шпаргалка по Postman (с учётом автоматизации и работы с API в реальных сценариях)

Учитывая твои задачи по автоматизации, скриптам и работе на VPS, здесь упор на то, что реально пригодится: коллекции, переменные, тесты и запуск через CLI.

---

## Базовые понятия

- **Request (запрос)** — отдельная HTTP-операция (GET/POST/etc) с URL, заголовками, телом и т.п.
- **Collection (коллекция)** — папка с запросами по логике проекта/API. Основа для автоматизации.
- **Environment (окружение)** — набор переменных (base URL, токены, ID) под конкретный контур (dev/stage/prod).
- **Variable (переменная)**:
    - `{{var}}` — подстановка в URL, headers, body.
    - Типы: глобальные, окружения, коллекции, локальные (в скрипте).
- **Pre-request Script** — JS-код, который выполняется _перед_ отправкой запроса (например, получить токен, посчитать подпись, задать timestamp).
- **Tests** — JS-код, который выполняется _после_ получения ответа (валидация статуса, полей, сохранение токенов в переменные).
- **Collection Runner** — запуск всей коллекции с итерациями, задержками и отчётом.
- **Newman** — CLI-версия Postman для CI/CD и скриптов (идеально под твои задачи автоматизации).

---

## Основные HTTP-методы и когда их использовать

|Метод|Назначение|Пример|
|---|---|---|
|GET|Получить данные (без изменения состояния)|`/users`, `/posts?page=2`|
|POST|Создать ресурс|`/users` (новый пользователь)|
|PUT|Полностью обновить ресурс|`/users/123` (все поля)|
|PATCH|Частично обновить ресурс|`/users/123` (только email)|
|DELETE|Удалить ресурс|`/users/123`|

---

## Интерфейс запроса: вкладки и для чего они нужны

- **Authorization** — выбор типа авторизации (API Key, Bearer Token, Basic Auth, OAuth 2.0 и др.). Удобно вынести в окружение, чтобы не копировать токены.
- **Headers** — добавить/изменить заголовки (Content-Type, Accept, кастомные). Часто используют для передачи `X-Request-ID`.
- **Params** — query-параметры в URL (например, `?page=1&limit=20`).
- **Body** — тело запроса: form-data, x-www-form-urlencoded, raw (JSON/XML), binary. Для API почти всегда используют raw + JSON.
- **Pre-request Script** — логика подготовки запроса.
- **Tests** — валидация ответа.
- **Cookies** — просмотр/редактирование кук (редко нужно для REST API).

## Частые сценарии и готовые сниппеты

### Сохранение токена из ответа в переменную окружения

Во вкладке **Tests**:

js

```js
const jsonData = pm.response.json();
pm.environment.set("auth_token", jsonData.access_token);
```

Теперь в других запросах можно использовать `{{auth_token}}` в заголовке `Authorization: Bearer {{auth_token}}`.

---

### Проверка статуса и полей в ответе

js

```js
pm.test("Status code is 200", () => {
  pm.response.to.have.status(200);
});

pm.test("Response has expected fields", () => {
  const jsonData = pm.response.json();
  pm.expect(jsonData).to.have.property("id");
  pm.expect(jsonData.id).to.be.a("number");
});
```

---

### Генерация подписи или вычисление значений перед запросом

Во вкладке **Pre-request Script**:

js

```js
const timestamp = Math.floor(Date.now() / 1000);
pm.variables.set("timestamp", timestamp);

// Пример: HMAC-подпись (псевдокод)
// const hmac = CryptoJS.HmacSHA256(data, secret).toString();
// pm.variables.set("signature", hmac);
```

Потом в Headers или Body используй `{{timestamp}}` и `{{signature}}`.

---

### Динамический base URL через переменную

В окружении задай: `base_url = https://api.dev.example.com`  
В запросе: `{{base_url}}/v1/users`  
Так легко переключаться между dev/stage/prod без правки URL.

## Коллекции и окружения: как правильно организовать

**Рекомендуемая структура:**

- Коллекция: `MyProject API`
    - Папка: `Auth` (логин, refresh)
    - Папка: `Users` (CRUD пользователей)
    - Папка: `Orders` (заказы)
- Окружения: `dev`, `stage`, `prod`
    - В каждом: `base_url`, `client_id`, `client_secret`, `auth_token` (последний обычно не хранят, а получают скриптом).

**Совет:** авторизацию (тип и параметры) лучше задать на уровне коллекции (Collection → Authorization), тогда все запросы унаследуют её.

## Запуск коллекций и автоматизация

### Collection Runner (в интерфейсе)

- Запускает все запросы в коллекции по порядку.
- Можно задать количество итераций и задержку между запросами.
- Показывает отчёт по тестам и ошибки.

### Newman (CLI) — для скриптов и CI/CD

Установка (Node.js должен быть установлен):

bash

```bash
npm install -g newman
```

Запуск коллекции:

bash

```bash
newman run collection.json --environment environment.json
```

Экспорт из Postman: File → Export (JSON).

**Полезные флаги:**

- `--iteration 10` — запустить 10 раз.
- `--delay-request 500` — пауза между запросами (мс).
- `--reporters cli,html` — вывод в консоль и HTML-отчёт.
- `--reporter-html-export report.html` — сохранить HTML.

Это идеально под твои задачи: можно положить в bash-скрипт на VPS, запускать по cron, сохранять отчёты и реагировать на падения тестов.

## Практические советы под твой стек (VPS, автоматизация, скрипты)

- **Не храни секреты в коллекциях.** Используй окружения и подменяй их при запуске Newman. В CI лучше передавать секреты через переменные окружения ОС.
- **Выноси всё, что меняется между контурами, в переменные:** base URL, порты, пути, флаги фич.
- **Делай атомарные тесты:** один тест = одна проверка (статус, поле, схема). Так проще понять, где ошибка.
- **Для сложных сценариев** (OAuth flow, цепочки запросов) используй Pre-request Script и сохраняй промежуточные данные в переменные.
- **Версионируй коллекции и окружения** в Git (формат JSON). Это даёт историю изменений и возможность ревью.

## Частые ошибки и как их избегать

- **«401 Unauthorized»**: проверь, что токен сохранён в переменной и подставляется в заголовок, а тип авторизации в Postman совпадает с тем, что ждёт API.
- **«400 Bad Request»**: проверь Content-Type (часто нужен `application/json`) и формат JSON (лишние запятые, кавычки).
- **«Timeout»**: проверь base URL и сеть (на VPS может быть блокировка или неверный DNS).
- **Переменные не подставляются**: убедись, что используешь правильный тип (`{{var}}`) и переменная существует в активном окружении.
- **Тесты не запускаются**: они выполняются только после получения ответа. Если запрос не ушёл (ошибка сети), тесты не сработают.

## Связь с твоими прошлыми задачами

- **Автоматизация проверки метрик на VPS.** Можно сделать коллекцию из 3–5 запросов к Prometheus/Grafana API, добавить тесты на пороговые значения и запускать через `newman` по cron. При падении тестов — отправлять уведомление в Telegram.
- **Node.js на VPS.** Postman — идеальный инструмент для тестирования своего API: коллекции для всех эндпоинтов, тесты на статус и схему ответа, запуск в CI перед деплоем.
- **Скрипты и синхронизация.** Newman позволяет превратить ручные тесты в воспроизводимые шаги, которые можно встроить в пайплайн деплоя.

## Быстрый старт-чеклист

1. Создай коллекцию `MyAPI`.
2. Создай окружение `dev` и добавь `base_url`.
3. Добавь запрос `GET {{base_url}}/health` и проверь ответ.
4. Добавь папку `Auth`, запрос на логин, тест для сохранения токена.
5. Добавь запросы к основным ресурсам, используй `{{auth_token}}`.
6. Экспортируй коллекцию и окружение в JSON, положи в Git.
7. На VPS установи `newman`, напиши bash-скрипт для запуска и отправки отчёта.
